Section 01
The Incident Problem
Modern cloud-native infrastructure generates thousands of telemetry signals per second — but the tools to make sense of them in real time have not kept pace with system complexity.

A production microservice environment is never truly static. Services scale, traffic patterns shift, dependencies fail, and code deploys introduce regressions. When something goes wrong, the on-call engineer is immediately presented with an overwhelming volume of signals: hundreds of Prometheus alerts, dozens of Grafana dashboards, a wall of error logs in Kibana, and dozens of Datadog traces — all simultaneously.

The fundamental challenge is not a shortage of observability data. It is the cognitive burden of correlating that data in real time, under pressure, to identify the failure mode, its root cause, the correct severity, and the projected time remaining before critical threshold breach.

What Sentinel AIOps Is
Sentinel is not a monitoring tool. It is an autonomous AI agent that transforms raw telemetry into classified, severity-graded, time-to-failure-predicted incident records — in real time.

Sentinel AIOps is a multi-layer agentic platform built around a LangGraph StateGraph — a directed graph of AI/ML analysis nodes that share a common state object and execute in sequence for every telemetry tick. Each node has exactly one responsibility, and the graph routes data through those responsibilities with conditional error handling.

Three Operating Modes
Mode 01
Historical Pipeline
Processes pre-generated simulator data from simulator_db.sqlite for model training, evaluation, and replay.
Mode 02
Live Feed Mode
Streams real-time simulated telemetry from live_feed_db.sqlite through the full 10-node inference pipeline.
Mode 03
Chat Query Mode
Enables natural-language queries over the incident database via an 11-node LLM-guarded QueryLangGraph agent.
Project Objectives

2

3

Telemetry Architecture

Temporal Correlation (n01_collect)

Every telemetry tick is correlated across all three pillars by (episode_id, timestamp). The collect node issues three sequential SQL queries against the same SQLite database:

n01_collect.py — temporal join
# Step 1: Fetch next metric row by monotonic id
metric = conn.execute("SELECT * FROM metrics WHERE id > ? LIMIT 1", (last_id,))

# Step 2: Fetch all log entries at the same (episode_id, timestamp)
logs   = conn.execute("SELECT log_level, exception_type, log_message
          FROM logs WHERE episode_id = ? AND timestamp = ?", (ep_id, ts))

# Step 3: Fetch all trace spans at the same (episode_id, timestamp)
spans  = conn.execute("SELECT * FROM traces WHERE episode_id = ? AND timestamp = ?", (ep_id, ts))

This produces a perfectly correlated snapshot: metrics, logs, and traces share the same episode_id and timestamp, guaranteeing that feature engineering receives a coherent multi-signal view of a single point in time.

Feature Engineering
Raw correlated telemetry — a metric row, a set of log entries, and a set of trace spans — is transformed into a 37-dimensional numeric feature vector that LightGBM can reason over in under a millisecond.

Node n02_feature_engineering is the boundary between raw observability data and machine-readable signal. It performs no ML — it is pure signal extraction, normalization, and encoding. Circuit Breaker Encoding

The circuit_breaker_state string is ordinally encoded before being passed to LightGBM — the ordinal order matches the failure progression.

# Ordinal encoding — must match training data
CB_ENCODE = {
    "closed":    0,  # Normal
    "half-open": 1,  # Recovering
    "open":      2,  # Failing
}
Design Decision

No dimensionality reduction (PCA, t-SNE) is applied before passing features to LightGBM. Gradient boosted trees handle 37 features efficiently without transformation — reducing features would risk losing the specific signal combinations (e.g., high heap_mb AND high gc_pause_p99) that distinguish MEMORY_LEAK from LATENCY_SPIKE.

Drain3 — Log Template Mining

Drain3 is a streaming log parser that identifies structured templates from free-text log messages. For example, the message "WARN heap=847MB gc_p99=312ms -- memory leak" is parsed into the template "WARN heap=<*>MB gc_p99=<*>ms -- memory leak". When Drain3 sees a template it has never encountered before, it sets log_has_novel_template = 1, which is a strong signal for failure mode transitions — particularly BAD_DEPLOY (where a new code deployment introduces entirely new log patterns) and CASCADING_FAILURE.

ML Classification — LightGBM
A LightGBM gradient-boosted tree classifier, tuned by Optuna's Tree-structured Parzen Estimator, identifies the failure mode from the 37-feature vector with sub-millisecond inference latency.
Why LightGBM?
AlternativeLimitation for SentinelLightGBM Advantage
XGBoostLevel-wise tree growth slower on wide dataLeaf-wise growth: faster convergence on 37 features
Random ForestNo sequential error correction; weaker on imbalanced dataBoosting corrects systematic errors between trees

Hyperparameter Tuning — Optuna TPE

Optuna's Tree-structured Parzen Estimator (TPE) sampler performs a directed Bayesian search over 9 hyperparameters. Each trial trains a LightGBM model and evaluates it on a held-out fold using macro-averaged F1, giving equal weight to all 13 failure mode classes regardless of frequency.

ConfigurationValueRationale
Trials80Practical sweet-spot for 9-parameter LightGBM search
CV Folds5StratifiedKFold: 20% per fold, stable per-class F1 estimates
Metricmacro F1Equal weight to all 13 classes; penalizes minority mode neglect
Early Stopping50 roundsStop adding trees if validation F1 hasn't improved in 50 rounds
Random Seed42Shared across Optuna, StratifiedKFold, and train/test split
Train/Test Split80/20Held-out test set never seen during tuning
Study Persistenceoptuna_study.dbSQLite-backed; interrupted tuning runs are resumable

At inference time, a single-row DataFrame is constructed from the 37-feature dict, ordered by the saved feature_names.json, and passed to the loaded model:

Graceful Degradation — Auto-Train

If lgbm_model.pkl is missing at pipeline startup, the classifier checks row count in engineered_features.csv. If MIN_TRAIN_ROWS = None (or enough rows exist), it launches train_classifier.py as a subprocess, blocks until completion, then loads the freshly trained model. While training, it returns "PENDING" with 0.0 confidence so downstream nodes can continue without crashing.

The LightGBM classifier identifies what kind of failure is occurring. The preliminary severity engine answers how bad is it right now — purely from threshold violations. Section 09
Tumbling Window — Label Smoother
Raw per-cycle classifier output is inherently noisy. The tumbling window accumulates 10 consecutive predictions and selects the majority label, suppressing transient misclassifications.

The LightGBM classifier makes a statistically independent decision every 500ms. Because real metrics have ±4% jitter, a MEMORY_LEAK episode might produce an occasional CPU_SATURATION or NONE prediction during a single anomalous tick. Without smoothing, the pipeline would fire false severity escalations and TTF forecasts for failure modes that were only momentarily dominant.

Node n05_tumbling_window uses a collections.deque(maxlen=10) buffer. Each cycle, the new prediction is appended (the oldest is dropped when full). A majority vote determines the dominant_state.

Mathematical Definition
dominant_state = argmaxmode (count of mode in buffer)
margin = voteswinner − votesrunner-up
buffer = deque of last N=10 predicted_failure strings
votesm = number of times mode m appears in buffer
margin = confidence indicator (high margin → stable dominant state)
Worked Example
CycleClassifier OutputBuffer ContentsDominant StateMarginWindow Full
1MEMORY_LEAK[ML]MEMORY_LEAK1No
3CPU_SATURATION[ML, ML, CS]MEMORY_LEAK1No
7MEMORY_LEAK[ML,ML,CS,ML,ML,ML,ML]MEMORY_LEAK5No
10MEMORY_LEAK[ML,ML,CS,ML,ML,ML,ML,ML,CS,ML]MEMORY_LEAK6Yes

At cycle 10: vote_distribution = {"MEMORY_LEAK": 8, "CPU_SATURATION": 2}, margin = 8−2 = 6.

Design Rules
What IS Smoothed

Only the label sequence (Y) — the string of predicted failure mode names across 10 cycles. This is the classifier's categorical output.

What is NOT Smoothed

Raw metric features. Averaging 10 cycles of CPU% would destroy genuine spikes. A CPU spike at cycle 8 would be diluted by 7 calm cycles before it.

Episode Boundary Behavior

The buffer is not reset when the episode_id changes. Labels carry forward across episode boundaries to prevent cold-start instability when a new episode begins. This means the window's dominant state reflects the recent historical trend, not just the current episode.

Output State Fields

Forecasting & Time-to-Failure
Each failure mode has a unique degradation trajectory. The forecasting engine routes the dominant failure state to a dedicated algorithm that computes the seconds remaining before a critical threshold breach.

Node n06_forecasting calls route_forecast(), which dispatches to one of 12 dedicated forecasting functions based on dominant_state. Each function maintains a per-episode rolling buffer of feature rows and fits its model to that buffer to compute the current slope or trajectory.

Forecasting Algorithms — Formulas
1. Linear Extrapolation
TTF = (Threshold − Current) ÷ Slope
Slope = Δvalue / Δtime (regression over buffer)
Threshold = critical breach value for this mode
TTF = seconds until breach (None if slope ≤ 0)

Used for: MEMORY_LEAK, DB_SLOWDOWN, CACHE_STAMPEDE, QUEUE_BACKUP, RETRY_STORM, DISK_IO_SATURATION

2. Exponential Growth
TTF = ln(Threshold / Current) ÷ r
r = exponential growth rate (fit to log of values)
ln = natural logarithm
TTF = None if Current ≥ Threshold (already breached)

Used for: CPU_SATURATION in accelerating phase

3. ARIMA (Auto-Regressive Integrated Moving Average)
yt = c + Σ φᵢ·yt−i + Σ θⱼ·εt−j + εt
φᵢ = autoregressive coefficients (past values)
θⱼ = moving-average coefficients (past errors)
εt = white noise error term
auto_arima from pmdarima selects optimal (p,d,q) order automatically
TTF is computed by finding the first forecast horizon where predicted value ≥ threshold
4. Multi-Feature Convergence (CASCADING_FAILURE)

Each feature's individual TTF is computed via its own algorithm. The minimum TTF across all features is reported, along with earliest_ttf_feature (which metric will breach first):

TTFfinal = min(TTFcpu, TTFmem, TTFp99, TTFerror, ...)
earliest_ttf_feature = the feature name with minimum TTF
Forecast Confidence Gate

Before a TTF estimate influences severity, it must pass a confidence gate. If forecast_confidence < 0.75 (min_confidence), the urgency_band defaults to "Distant" regardless of TTF value. This prevents premature severity escalation when the forecast model has insufficient history (buffer length < minimum required cycles).

Reliability & Survival Analysis
Beyond detecting that a failure is happening, Sentinel quantifies the historical probability of system survival — how long episodes of this type typically last before they terminate or resolve.

Node n08_reliability applies Kaplan-Meier non-parametric estimation and 2-Parameter Weibull Maximum Likelihood Estimation to the historical episode database. Together, these tell the dashboard: "given that this service is in a MEMORY_LEAK episode that has been running for 90 seconds, what is the survival probability?"

Four Failure Mode Groups (Weibull Stratification)
GroupFailure ModesExpected βBehavior
Immediate TriggerBAD_DEPLOY, CACHE_STAMPEDE, CASCADING_FAILURE, CPU_SATURATION, DEPENDENCY_TIMEOUT, ERROR_STORM> 1Wear-out; failure rate increases over time
Fast AccumulationQUEUE_BACKUP, RETRY_STORM> 1Rapid growth pattern, high early failure rate
Progressive DegradationDISK_IO_SATURATION≈ 1Near-constant hazard rate
Slow / Latent DegradationDB_SLOWDOWN, MEMORY_LEAK, LATENCY_SPIKE< 1 → 1+Slow onset; hazard increases late
Kaplan-Meier Non-Parametric Survival Estimate

The KM estimator computes a step-function survival curve from historical episode durations, handling right-censored episodes (episodes that ended before resolution):

S(t) = ∏tᵢ ≤ t (1 − dᵢ / nᵢ)
dᵢ = number of episodes that ended (failed) at time tᵢ
nᵢ = number of episodes at risk just before tᵢ (not yet ended or censored)
S(0) = 1.0 (all episodes survive at time zero)

Greenwood Standard Error — 95% confidence interval for the KM curve:

SE(t) = S(t) × √( Σtᵢ ≤ t dᵢ / (nᵢ(nᵢ − dᵢ)) )
2-Parameter Weibull Maximum Likelihood Estimation

The Weibull distribution models failure time with two parameters: β (shape/slope) and η (scale/characteristic life):

f(t; β, η) = (β/η) · (t/η)^(β−1) · exp(−(t/η)^β)
R(t) = exp(−(t/η)^β) [Survival / Reliability function]
h(t) = (β/η) · (t/η)^(β−1) [Hazard rate]
β < 1: decreasing hazard rate (early failures; "burn-in" period)
β = 1: constant hazard rate (random / exponential failure)
β > 1: increasing hazard rate (wear-out; most production failure modes)
η: scale parameter — time at which 63.2% of episodes have ended
MLE Fitting Priority
1
reliability library (Reid) — Primary
Most accurate for small samples; handles right-censored data with Fit_Weibull_2P()
2
lifelines (Davidson-Pilon) — Secondary
WeibullFitter().fit(); rho_ → β, lambda_ → η
3
SciPy L-BFGS-B — Fallback
Native negative log-likelihood minimization; always available
Runtime Survival Probability

In the live pipeline, pre-fitted Weibull parameters (weibull_params.json) are loaded once at startup. For each cycle, the current episode's elapsed_s is used to compute survival probability:

P(survival at elapsed_s) = exp(−(elapsed_s / η)^β)
Written to state as survival_probability, displayed in the frontend ReliabilityCard.

SSE Broadcaster Architecture
sse_broadcaster.py — thread-safe SSE push
class SSEBroadcaster:
    _lock:          threading.Lock   # protects _latest_state
    _latest_state:  dict             # most recent pipeline state

    @classmethod
    def update(cls, state: dict):          # called from pipeline thread (sync)
        with cls._lock:
            cls._latest_state = safe_serialize(state)

    @classmethod
    async def stream(cls, interval_s=0.5):  # async generator for FastAPI
        while True:
            payload = LiveFeedService.get_live_feed_state()
            yield f"data: {json.dumps(payload)}\n\n"
            await asyncio.sleep(interval_s)

The pipeline thread (synchronous) calls SSEBroadcaster.update() after every n10_db_writer cycle. The FastAPI SSE endpoint uses an async generator that yields the latest enriched dashboard payload every 500ms to all connected clients simultaneously. Thread safety is guaranteed by the threading.Lock.

Process Management via API

POST /api/live/start spawns two subprocesses stored as module-level globals _live_feed_proc and _langgraph_proc. Liveness is checked with proc.poll() is None. Termination uses proc.terminate() which sends SIGTERM, allowing graceful shutdown. The subprocess approach avoids threading complexity while giving the API full lifecycle control.

WAL Mode — Why It Matters

SQLite's default journal mode locks the database file during writes, which would block the LangGraph reader while the simulator is writing. WAL (Write-Ahead Logging) mode appends writes to a separate WAL file without blocking readers. Readers see the last committed checkpoint; the writer never locks the main database file.

DbWriter.setup() — WAL configuration

conn.execute("PRAGMA synchronous=NORMAL")  # faster, still crash-safe
conn.execute("PRAGMA foreign_keys=ON")     # referential integrity

Section 22
Conclusion
Sentinel AIOps demonstrates that the knowledge required for expert-level incident management can be encoded, structured, and executed autonomously — making institutional knowledge permanent and scalable.

Production infrastructure generates more observability data than any human can process in real time. Sentinel's architecture accepts that premise and builds around it: the system correlates, the system classifies, the system forecasts, the system escalates — and then it tells the human what it found and why.

Every design decision in Sentinel has an engineering reason. LangGraph was chosen because its StateGraph allows each analysis node to have a single, testable responsibility and a clear interface (the shared state dict). LightGBM was chosen because gradient boosted trees make no assumptions about feature normalization and produce calibrated probability outputs that gate downstream decisions. WAL-mode SQLite was chosen because it allows concurrent access from multiple processes without a message broker.

The Architecture's Golden Rules
  1. Telemetry is correlated before intelligence is applied. Metrics, logs, and traces are joined by (episode_id, timestamp) before any feature is extracted.
  2. Each pipeline node has exactly one responsibility. Collection, engineering, severity, classification, smoothing, forecasting, and persistence are distinct nodes — not mixed concerns.
  3. Rule-based and ML classification are complementary. Preliminary severity (P1–P4 rules) answers "how bad is it now"; LightGBM answers "what kind of failure is this" — both are needed.
  4. Label stability is the responsibility of the tumbling window. Raw per-cycle classifier output is inherently noisy; the 10-cycle majority vote provides the stable label that forecasting and severity update rely on.
  5. Forecasting contributes urgency, not severity. Time-to-failure estimates gate the urgency_band which feeds into the severity matrix — forecasting influences severity but does not set it directly.
  6. Escalation is immediate; de-escalation is earned. A severity jump fires instantly. A severity drop requires 5 consecutive confirming cycles (the hysteresis dwell counter).
  7. Human Gate preserves operator accountability. Large severity jumps require explicit human confirmation or auto-timeout; every decision is logged to the audit table.
  8. The database is the source of truth, not in-memory state. Every pipeline cycle writes to SQLite before the SSE broadcast; the API reads from the database, not from in-process variables.
  9. The chatbot is a read-only intelligence layer. QueryLangGraph queries incident data and synthesizes language — it never modifies state, triggers pipeline actions, or escalates incidents.
  10. Graceful degradation is designed, not accidental. Missing model → auto-train. No data → retry after poll interval. Node failure → db_writer writes partial state → checkpoint resume.
